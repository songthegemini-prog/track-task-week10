# SDLC Spec

เปลี่ยนโจทย์ของผู้ใช้ให้เป็นเอกสารที่คนอ่านเข้าใจ และ Codex ใช้เป็นบริบทในขั้นถัดไปได้ ขั้นนี้**ยังไม่เขียนโค้ดแอป**


## คุยกับผู้ใช้ที่ไม่ใช่โปรแกรมเมอร์

- ตอบเป็นภาษาไทยที่เข้าใจง่าย อธิบายศัพท์เทคนิคสั้น ๆ ในวงเล็บทุกครั้งที่ใช้ครั้งแรก
- สรุปการเปลี่ยนแปลงเป็นภาษาคน ไม่ต้องให้ผู้ใช้อ่านโค้ดทุกบรรทัด
- จบงานด้วยหัวข้อ **"สิ่งที่คุณต้องทำเอง"** เป็นข้อที่คลิกหรือพิมพ์ตามได้ทันที (เมนูไหน ปุ่มไหน วางอะไร)

## เริ่มจากสิ่งที่มีอยู่

- อ่านคำขอ ไฟล์ที่ผู้ใช้อ้างถึง และเอกสารเดิมใน `docs/` ก่อน ถ้ามีอยู่แล้วให้แก้เฉพาะส่วนที่เปลี่ยน ไม่เขียนทับทั้งไฟล์
- ถ้าผู้ใช้หรือผู้สอนเตรียม `docs/plan.md` และ `docs/requirements.md` ไว้แล้ว ให้ถือเป็นข้อกำหนดที่ตกลงแล้ว **ไม่แก้สองไฟล์นี้เอง** อ่านแล้วข้ามไปทำขั้น Design ถ้าพบจุดที่ขัดกันหรือไม่ชัด ให้แจ้งเป็นรายการคำถามแทนการแก้
- ถามเฉพาะสิ่งที่ถ้าเดาผิดแล้วระบบจะผิดความหมาย เช่น ใครเห็นข้อมูลของใครได้ หรือใครแก้อะไรได้บ้าง สิ่งอื่นให้ระบุเป็นสมมติฐานที่แก้ได้ แล้วทำต่อ
- ใช้ stack ที่โปรเจกต์กำหนด ค่าเริ่มต้นของ workshop นี้คือ Next.js + Supabase (Postgres, Auth, RLS) + Vercel

## 1. Planning → `docs/plan.md`

- ปัญหา ผู้ใช้แต่ละกลุ่ม และเป้าหมาย
- ขอบเขต MVP: **ทำในรอบนี้** และ **ไม่ทำในรอบนี้** (ต้องมีทั้งสองหัวข้อ)
- ความเสี่ยงและข้อจำกัด เช่น เวลา ข้อมูลส่วนบุคคล หรือบริการที่ใช้แบบฟรี

## 2. Requirements → `docs/requirements.md`

- เขียน user story ในรูปแบบ "ในฐานะ [ใคร] ฉันต้องการ [ทำอะไร] เพื่อ [ประโยชน์]" ใส่เลขกำกับ (US-1, US-2, …) เพื่อให้อ้างถึงในขั้นต่อไปได้
- ใส่เกณฑ์ยอมรับใต้ทุก story เป็นข้อที่ทดสอบได้จริง ระบุสภาพตั้งต้น การกระทำ และผลที่คาดหวัง
- ต้องมีเกณฑ์ด้านสิทธิ์ทุกครั้งที่มีข้อมูลรายบุคคล เช่น "บัญชี A ไม่เห็นข้อมูลของบัญชี B"
- ใส่กรณีผิดพลาดที่กระทบกติกา เช่น ไม่มีสิทธิ์ทำ ข้อมูลซ้ำ หรือยังไม่ล็อกอิน

## 3. Design → `docs/design.md` และ `AGENTS.md`

- **Data model:** ตาราง คอลัมน์ ชนิดข้อมูล คีย์ ความสัมพันธ์ และ unique constraint ใช้ `user_id uuid references auth.users` เมื่อข้อมูลเป็นของผู้ใช้
- **ตารางสิทธิ์ (access matrix):** ทุกตาราง × บทบาท (เช่น `anon`, เจ้าของข้อมูล, หัวหน้าทีม, สมาชิกทีม, คนนอกทีม) × การกระทำ (select / insert / update / delete) ตารางนี้คือแบบของ RLS policy
- **ข้อมูลที่ต้องเข้าถึงก่อนมีสิทธิ์:** ถ้าผู้ใช้ต้องใช้ข้อมูลที่ RLS ยังไม่ให้อ่าน เช่น ตรวจรหัสเชิญก่อนเข้าทีม ให้ออกแบบเป็น function ที่ตรวจและคืนเฉพาะผลที่จำเป็น ไม่เปิดสิทธิ์อ่านทั้งตาราง
- **กติกาที่กระทบความถูกต้องของข้อมูล** เช่น 1 คนอยู่ได้ 1 ทีม หรือผู้รับงานแก้ได้แค่สถานะ ต้องบังคับที่ฐานข้อมูล (constraint, trigger หรือ function) การปิดปุ่มบนหน้าจอเป็นแค่ความสะดวก
- **ผังหน้าจอ:** route ของแต่ละหน้า และ user story ที่หน้านั้นรองรับ
- **`AGENTS.md`** ที่ root ของโปรเจกต์ ใช้แม่แบบใน [references/agents-template.md](references/agents-template.md) แล้วเติมคำสั่งรันและทดสอบจริงของโปรเจกต์

รูปแบบของเอกสารทั้งสามไฟล์อยู่ใน [references/doc-templates.md](references/doc-templates.md) ใช้เฉพาะหัวข้อที่จำเป็น

## ส่งงาน

สรุปให้ผู้ใช้สั้น ๆ ว่าเขียนหรือแก้ไฟล์อะไร มีสมมติฐานใดที่ควรยืนยัน และงานชิ้นแรกที่ควรสั่งในขั้น Implementation (แนะนำให้ใช้ `$supabase-feature` ทีละ user story)
