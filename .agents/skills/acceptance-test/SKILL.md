# Acceptance Test

ตอบให้ได้ว่าระบบผ่านเกณฑ์ยอมรับข้อไหนแล้ว ด้วยหลักฐานจากการรันจริง แยกสิ่งที่คาดหวัง สิ่งที่สังเกตได้ และสิ่งที่ยังตรวจไม่ได้ออกจากกันเสมอ


## คุยกับผู้ใช้ที่ไม่ใช่โปรแกรมเมอร์

- ตอบเป็นภาษาไทยที่เข้าใจง่าย อธิบายศัพท์เทคนิคสั้น ๆ ในวงเล็บทุกครั้งที่ใช้ครั้งแรก
- สรุปการเปลี่ยนแปลงเป็นภาษาคน ไม่ต้องให้ผู้ใช้อ่านโค้ดทุกบรรทัด
- จบงานด้วยหัวข้อ **"สิ่งที่คุณต้องทำเอง"** เป็นข้อที่คลิกหรือพิมพ์ตามได้ทันที (เมนูไหน ปุ่มไหน วางอะไร)

## เตรียม

- อ่าน `docs/requirements.md` และระบุเกณฑ์ยอมรับ (AC) ที่อยู่ในขอบเขตของคำขอ ถ้าไม่มีเอกสาร ให้ถามผู้ใช้ว่าจะใช้อะไรเป็นผลที่คาดหวัง
- **ค่าเริ่มต้นคือรายการทดสอบด้วยมือ** ที่ผู้ใช้กดตามได้ทีละขั้น เพราะผู้ใช้ส่วนใหญ่ไม่ใช่โปรแกรมเมอร์ เขียน test อัตโนมัติเฉพาะเมื่อผู้ใช้ขอ หรือโปรเจกต์มีเครื่องมือทดสอบอยู่แล้ว และต้องขออนุญาตก่อนเพิ่ม dependency
- ทดสอบกับฐานข้อมูลฝึกหรือข้อมูลจำลองเท่านั้น ถ้าต้องสร้างหรือลบข้อมูลในฐานข้อมูลจริง ให้ขออนุญาตก่อน

## ทดสอบ

1. ทำตาราง AC → วิธีทดสอบ (อัตโนมัติ หรือ ด้วยมือ) → ผลที่คาดหวัง
2. เขียนขั้นตอนทดสอบด้วยมือของแต่ละ AC (เปิดหน้าไหน กดอะไร ควรเห็นอะไร) ถ้าเขียน test อัตโนมัติ ให้ตั้งชื่ออ้างเลข AC เช่น `AC-3.3 สมาชิกที่ไม่ใช่หัวหน้าสร้างงานไม่ได้`
3. สิ่งที่ Codex ตรวจเองได้ (lint, build, test อัตโนมัติ, อ่านโค้ดเทียบ AC) ให้รันหรือตรวจแล้วรายงานผลจริง สิ่งที่ต้องกดในเบราว์เซอร์ให้ระบุว่า "รอผู้ใช้ทดสอบ" ห้ามสรุปว่า "ผ่าน" ถ้าไม่ได้ตรวจ
4. test ที่ไม่ผ่าน: อธิบายว่าโค้ดผิดหรือ test ผิด ก่อนแก้ ห้ามแก้ test ให้ผ่านโดยเปลี่ยนผลที่คาดหวังเอง ถ้าข้อกำหนดไม่ชัด ให้ถามผู้ใช้
5. AC ด้านสิทธิ์ต้องมีรายการทดสอบด้วยหลายบัญชีเสมอ (หัวหน้า, สมาชิก และคนนอกทีม ตามตาราง "บัญชีสำหรับทดสอบ" ใน `docs/requirements.md`) ถ้าทดสอบอัตโนมัติไม่ได้ ให้เขียนขั้นตอนทดสอบด้วยมือที่ชัดเจน
6. ทดสอบกรณีผิดพลาดที่อยู่ในเกณฑ์ เช่น ยังไม่ล็อกอิน ไม่มีสิทธิ์ทำ หรือรหัสเชิญผิด ไม่ใช่แค่ทางที่สำเร็จ

## ตรวจบน URL ที่ deploy แล้ว

- ยืนยันก่อนว่ากำลังตรวจ URL และ environment ไหน (Preview หรือ Production)
- เปิดหน้าหลักและทำเส้นทางหลักตาม AC ถ้ามีเครื่องมือเปิดเบราว์เซอร์ ถ้าไม่มี ให้เขียน checklist ให้ผู้ใช้ทำเอง
- ถ้าบนเครื่องผ่านแต่บน URL จริงไม่ผ่าน ให้สงสัย env vars และ Redirect URLs ของ Supabase ก่อน

## รายงาน

ใช้ตารางนี้ แล้วสรุปว่าผ่านกี่ข้อจากทั้งหมด และสิ่งที่ผู้ใช้ต้องทำต่อ

| AC | วิธี | ผลที่คาดหวัง | ผลจริง | สถานะ (ผ่าน / ไม่ผ่าน / ยังไม่ได้ตรวจ) |
|---|---|---|---|---|

ย้ำกับผู้ใช้ว่า test ผ่านไม่ได้แปลว่าระบบถูกต้องเสมอไป ควรอ่านว่าแต่ละ test ตรวจอะไรจริง
