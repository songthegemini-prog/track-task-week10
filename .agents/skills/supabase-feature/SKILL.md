# Supabase Feature

สร้างฟีเจอร์ทีละชิ้นให้ตรงข้อกำหนด และปลอดภัยตั้งแต่แรก งานหนึ่งรอบควรจบที่ user story เดียว


## คุยกับผู้ใช้ที่ไม่ใช่โปรแกรมเมอร์

- ตอบเป็นภาษาไทยที่เข้าใจง่าย อธิบายศัพท์เทคนิคสั้น ๆ ในวงเล็บทุกครั้งที่ใช้ครั้งแรก
- สรุปการเปลี่ยนแปลงเป็นภาษาคน ไม่ต้องให้ผู้ใช้อ่านโค้ดทุกบรรทัด
- จบงานด้วยหัวข้อ **"สิ่งที่คุณต้องทำเอง"** เป็นข้อที่คลิกหรือพิมพ์ตามได้ทันที (เมนูไหน ปุ่มไหน วางอะไร)

## ก่อนแก้

- อ่าน `AGENTS.md`, `docs/requirements.md` และ `docs/design.md` แล้วระบุว่ากำลังทำ user story และเกณฑ์ยอมรับข้อไหน ถ้าไม่มีเอกสาร ให้ถามสั้น ๆ หรือแนะนำให้ใช้ `$sdlc-spec` ก่อน
- ตรวจรุ่นของ Next.js, `@supabase/supabase-js` และ `@supabase/ssr` ใน `package.json` ถ้าไม่แน่ใจวิธีเรียก API ของรุ่นนั้น ให้ดูจากโค้ดที่ติดตั้งหรือเอกสารทางการ ไม่เดาจากความจำ
- ใช้โครงสร้าง client เดิมของโปรเจกต์ (starter ของ workshop มี `lib/supabase/client.ts`, `lib/supabase/server.ts` และ `proxy.ts` ให้แล้ว) ถ้ายังไม่มี ให้ตั้งตาม [references/client-setup.md](references/client-setup.md)

## ฐานข้อมูล

1. เขียนการเปลี่ยนโครงสร้างเป็นไฟล์ใหม่ใน `supabase/migrations/` ตั้งชื่อ `<YYYYMMDDHHMMSS>_<สิ่งที่ทำ>.sql` ไม่แก้ไฟล์ migration ที่รันไปแล้ว
2. **ทุกตารางใหม่ต้อง `enable row level security`** และมี policy ตามตารางสิทธิ์ใน `docs/design.md` แยก policy ตามการกระทำ ระบุ `to` role ทุกครั้ง ใช้ `(select auth.uid())` และสร้าง index ให้คอลัมน์ที่ policy ใช้กรอง รูปแบบอยู่ใน [references/rls-patterns.md](references/rls-patterns.md)
3. บังคับกติกาที่กระทบความถูกต้องในฐานข้อมูล เช่น unique constraint ให้ 1 คนอยู่ได้ 1 ทีม หรือ trigger ที่ให้ผู้รับงานแก้ได้แค่สถานะ ไม่พึ่งการซ่อนปุ่มบนหน้าจออย่างเดียว
4. งานที่ต้องอ่านข้อมูลที่ RLS ยังไม่ให้อ่าน (เช่น ตรวจรหัสเชิญเข้าทีม) หรือการตรวจสิทธิ์ที่ต้อง query ตารางเดียวกัน ให้ทำเป็น function ที่คืนเฉพาะผลที่จำเป็น ถ้าเป็น `security definer` ต้อง `set search_path = ''`, อ้างชื่อตารางเต็ม และคืนเฉพาะข้อมูลที่จำเป็น
5. **ห้ามรัน SQL กับฐานข้อมูลของผู้ใช้เอง** ให้บอกชื่อไฟล์ แล้วเขียนขั้นตอนให้ผู้ใช้ทำเอง: Supabase → SQL Editor → New query → วางเนื้อหาไฟล์ → Run (ใช้ `supabase db push` ได้เฉพาะเมื่อโปรเจกต์ link CLI ไว้แล้วและผู้ใช้อนุญาต)

## แอป

- ฝั่ง browser ใช้ `NEXT_PUBLIC_SUPABASE_URL` และ `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` เท่านั้น
- `SUPABASE_SECRET_KEY` ใช้ได้เฉพาะโค้ดฝั่ง server ที่จำเป็นต้องข้าม RLS จริง ๆ เช่นงานของผู้ดูแลระบบ และต้องตรวจสิทธิ์ผู้เรียกเองก่อนเสมอ งานปกติของผู้ใช้ให้ใช้ server client ที่ผูก session ผู้ใช้ เพื่อให้ RLS ทำงาน
- ตรวจผู้ใช้ฝั่ง server ด้วยวิธีที่ตรวจ token กับ Supabase ตามเอกสารของรุ่นที่ใช้ ไม่เชื่อ `user_id` ที่ส่งมาจากฟอร์ม
- หน้าจอต้องมีสถานะ กำลังโหลด / ไม่มีข้อมูล / ผิดพลาด / สำเร็จ และแสดงข้อความผิดพลาดที่ผู้ใช้เข้าใจ ไม่แสดงรายละเอียดภายในหรือค่าลับ
- งานที่ต้องส่งอีเมล (เช่น US-6) ให้ทำตาม [references/email-gmail-smtp.md](references/email-gmail-smtp.md)
- ถ้าต้องเพิ่ม env var ให้เพิ่มชื่อและค่าตัวอย่างลงใน `.env.example` และตรวจว่า `.gitignore` กันไฟล์ `.env.local` อยู่ (เช่นมีบรรทัด `.env*` หรือ `.env*.local`)

## ตรวจก่อนส่ง

- รัน lint, test และ build ที่โปรเจกต์มี แล้วรายงานผลจริง ถ้ารันไม่ได้ ให้บอกเหตุผล
- สรุป: user story ที่ทำ, ไฟล์ที่แก้, ไฟล์ SQL ที่ผู้ใช้ต้องรัน, env var ที่ต้องตั้ง และขั้นตอนทดสอบด้วยมือตามเกณฑ์ยอมรับ รวมถึงการทดสอบด้วย 2 บัญชีเมื่อเกี่ยวกับสิทธิ์
- แนะนำให้ผู้ใช้อ่าน diff แล้ว commit ก่อนเริ่ม user story ถัดไป
